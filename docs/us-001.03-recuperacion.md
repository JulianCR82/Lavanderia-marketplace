# US-001.03 — Recuperar acceso

Implementación y validación: **2026-11-23**. El usuario aprobó el plan completo.
API y cliente implementados; recorrido real web y Android confirmado por el usuario.
Estado: **Hecha**, con trazabilidad conciliada el **2026-11-24**. La prueba Android
se confirmó el 2026-11-23 y se ratificó el 2026-11-24; iOS y preparación para
distribución conservan sus pendientes. Las [decisiones oficiales](decisiones-autenticacion.md) y el
[backlog](historias-usuario.md) conservan el alcance vigente.

## Comportamiento

Desde «Olvidé mi contraseña»: correo → código → contraseña nueva y confirmación
→ confirmación → ingreso con la nueva contraseña. No se inicia sesión al cambiarla.
El cliente reutiliza tema, campos y botones existentes, con ancho de formulario
limitado, desplazamiento, adaptación al teclado y mensajes accesibles. Las pruebas
de tipos/exportación no sustituyen verificar teclado, texto grande y pantallas
pequeñas en un dispositivo.

Un correo con contraseña, uno inexistente y uno que solo usa Google reciben el
mismo contrato público. Solo el primero recibe código. La recuperación no crea
credenciales ni vincula proveedores. El ingreso con Google previamente vinculado
sigue disponible. Si se perdió el correo, recuperar ese canal con su proveedor o
utilizar un método ya vinculado; no existe un acceso alternativo de soporte.

## Contrato HTTP

Todas las rutas son públicas explícitas, validan DTO con lista de campos permitidos
y responden `Cache-Control: no-store`. No enviar pruebas en URL ni registrarlas.

| Método y ruta | Entrada | Resultado correcto |
| --- | --- | --- |
| POST `/auth/recovery` | `email` | 202: `recoveryId`, `expiresAt`, `resendAvailableAt`, mensaje genérico |
| POST `/auth/recovery/resend` | `recoveryId` | 202: mismo contrato, código anterior invalidado |
| POST `/auth/recovery/verify` | `recoveryId`, `code` | 200: `resetToken`, `expiresAt` |
| POST `/auth/recovery/reset` | `resetToken`, `password`, `passwordConfirmation` | 200: `status: PASSWORD_CHANGED`, mensaje de ingreso posterior |

Normalización de correo igual al ingreso: recorte y minúsculas; máximo 254
caracteres. Código de seis dígitos, UUID v4 y autorización base64url de 43 caracteres.
Errores de prueba: 400 `RECOVERY_INVALID`; confirmación diferente:
400 `PASSWORD_MISMATCH`. Cuotas: 429 con `retryAfterSeconds`. Fallos internos se
sanitizan como 503 sin exponer SQL, correo ni respuesta del proveedor.

## Controles y persistencia

- Proceso OTP de diez minutos y cinco fallos. Reenvío después de sesenta segundos;
  rotación del código sin ampliar vigencia ni devolver intentos. Reiniciar dentro
  de esos diez minutos conserva fallos y vencimiento e invalida el proceso anterior.
- OTP HMAC ligado a propósito, desafío y correo. Autorización aleatoria de 32 bytes,
  cinco minutos, protegida por HMAC y consumida una sola vez. Nunca equivale al
  token de sesión. Código/autorización del cliente viven en memoria, sin almacenamiento.
- Política de contraseña existente: 15–128 puntos de código Unicode, espacios y
  gestores admitidos, bloqueo local de contraseñas comunes y Argon2id.
- Transacción con conexión dedicada y bloqueo compartido con registro. Al cambiar:
  bloquear credencial, comprobar que no cambió desde la solicitud, actualizar hash,
  revocar todas las sesiones, consumir pruebas y registrar `PASSWORD_RESET` con
  cuenta/fecha. Se elimina del desafío consumido el hash anterior y las pruebas.
- El ingreso por contraseña vuelve a comprobar el hash bajo bloqueo antes de
  crear una sesión: un ingreso que verificó la contraseña anterior no puede emitir
  una sesión después de que el restablecimiento haya ganado la carrera.
- Cuotas compartidas de `REGISTRATION_*`: correo/hora, IP/hora, global/hora y
  global/día; también comparten pausa de envío y límite de solicitudes por IP.
  Los contactos no elegibles reservan cuota. No hay bloqueo permanente de ingreso.
- El envío OTP es asíncrono y el endpoint inicial aplica piso de 200 ms más
  variación de 0–50 ms. Esto reduce diferencias simples de tiempo; no garantiza
  indistinguibilidad absoluta bajo todas las cargas. Registro conserva su decisión
  independiente de informar duplicados; la recuperación no elimina esa exposición.
- El OTP no se persiste en claro: un reinicio antes del envío requiere reenvío.
  `delivery_state` permite diagnóstico técnico sin revelar el código al cliente.
- El aviso posterior tiene cola persistente, arrendamiento de un minuto, reintento
  cada sesenta segundos y clave idempotente Resend. Consume las mismas cuotas;
  un fallo de aviso no revierte el cambio de contraseña ya confirmado.
- Desafíos y avisos tienen retención de 24 horas, purgada durante actividad del
  módulo. Los avisos que no pudieron entregarse dentro de esa ventana se descartan.
  La auditoría de seguridad no se purga con los desafíos.

Migración nueva: `apps/api/migrations/004_password_recovery.sql`. No se modificaron
migraciones aplicadas ni se eliminaron cuentas, volúmenes o datos del usuario.

## Organización del código

`apps/api/src/recovery/` separa controlador/DTO, reglas, persistencia y entrega.
`AccountSecurityModule` comparte configuración, HMAC, almacenamiento de cuotas y
límites existentes sin duplicar proveedores. `mail/resend-transport.ts` comparte
el transporte entre registro y recuperación. Los nombres de entorno existentes
se conservan; esta historia no requiere nuevas claves ni dependencias.

`apps/mobile/src/features/recovery/` separa contrato API, estado del recorrido y
presentación. `src/app/recuperar.tsx` contiene solo integración de ruta/sesión.
El ingreso añade el acceso al formulario; no se cambiaron configuración nativa,
roles ni permisos de negocio. No hace falta reconstruir APK por este cambio JavaScript.

## Evidencia y límites de validación

- Migración 004 aplicada al PostgreSQL 17 local; historial 001–004 confirmado.
- API: ESLint, compilación, tipos y seis pruebas unitarias aprobados.
- E2E de regresión: 38 pruebas, cinco suites, PostgreSQL 17 en base desechable
  aislada. Incluyen respuesta genérica, cuotas compartidas, código incorrecto,
  expiración, reenvío, reinicio sin devolver intentos, concurrencia de consumo,
  autorización caducada/ajena, credencial obsoleta, revocación y carrera con ingreso.
  También fallos/reintento del transporte y validación de campos extra.
- Móvil: ESLint y tipos aprobados; exportaciones web, Android e iOS generadas.
- API y `/recuperar` web: respuesta local comprobada. El usuario confirmó recepción
  real Resend, «Contraseña actualizada» e ingreso al panel con la nueva contraseña.
  Reportó inicialmente un fallo de conexión al ingresar; tras Ctrl+F5 ingresó
  correctamente. No se reprodujo en API; posible coincidencia con recreación de
  servicios, sin causa concluyente. No se relajaron controles para resolverlo.
- La automatización visual no pudo inicializarse durante la implementación. Esa
  limitación no invalida la prueba manual posterior: el 2026-11-23, tras recibir
  la guía del emulador Android con el APK existente, el usuario confirmó «Probado
  y funcionando»; el 2026-11-24 reiteró haber realizado la prueba y pidió conciliar
  la trazabilidad. El recorrido Android queda validado por reporte del usuario,
  sin atribuir observación directa al agente ni casos individuales no detallados.
- La prueba funcional iOS y la revisión específica de teclado/texto ampliado no
  están acreditadas. Se conservan como validaciones de plataforma y accesibilidad
  pendientes para distribución; no se vuelve a solicitar la prueba Android ya
  confirmada. Las exportaciones no acreditan comportamiento visual ni Google iOS.
- El remitente `onboarding@resend.dev` sigue limitado a pruebas de la cuenta Resend;
  dominio propio/verificación y entrega a otros destinatarios siguen pendientes
  para distribución. Esta implementación no cambia esa limitación compartida.

## Repetir la prueba

Con API/Metro activos, abrir `http://localhost:8081/recuperar` o «Olvidé mi
contraseña» en Expo Go/development build. Usar un correo ya registrado que pueda
recibir mensajes con la configuración Resend actual. Completar código y contraseña
nueva; ingresar después, comprobar que la anterior falla y que una sesión anterior
de otro dispositivo queda invalidada al llamar a la API. No compartir claves ni códigos.

Para cambios de código, usar Compose Watch o reconstruir/recrear los servicios
afectados según README. No ejecutar una reconstrucción mientras se completa una
prueba manual, porque interrumpe temporalmente las peticiones. Si el ingreso informa
error de conexión tras un cambio confirmado, comprobar salud de API/Metro y reintentar
el ingreso; no repetir automáticamente el restablecimiento ni asumir que se revirtió.

Pruebas técnicas desde la raíz, con Docker activo:

```powershell
docker compose exec api pnpm --dir apps/api exec eslint "{src,apps,libs,test}/**/*.ts"
docker compose exec api pnpm build:api
docker compose exec api pnpm --dir apps/api test --runInBand
docker compose exec api env REGISTRATION_TEST_POSTGRES=1 pnpm --dir apps/api test:e2e --runInBand
docker compose exec mobile pnpm lint
docker compose exec mobile pnpm exec tsc --noEmit
```
