# US-001.01 — Registro de clientes

## Alcance de desarrollo revisado — 2026-11-25

El usuario decidió mantener Resend con el remitente de prueba durante el desarrollo
del MVP y aplazar dominio/remitente propios. Ese requisito operativo deja de bloquear
el alcance de desarrollo; sigue pendiente antes de enviar a otros destinatarios o
distribuir el producto. El dominio `resend.dev` solo permite enviar al correo asociado
a la cuenta Resend. Registro, recepción de OTP e ingreso automático ya tienen la
evidencia real reportada por el usuario en la guía de acceso.

Esta decisión no acredita escenarios manuales nuevos ni prueba iOS. Las validaciones
de registro que seguían pendientes conservan su estado; se retira únicamente el
dominio propio como bloqueo de desarrollo. US-001.01 continúa en curso por esas
validaciones restantes, sin confundir un cambio de alcance con una ejecución nueva.
No se modifica código, configuración, proveedor, cuotas ni verificación OTP.

## Historial de implementación y validación

Implementación iniciada el 2026-11-22. La historia sigue **en curso** hasta comprobar
entrega real con Resend y el flujo Android/iOS. Las pruebas Docker y la medición
de Argon2id se completaron en la comprobación posterior de esta sesión.
Rigen los [criterios del backlog](historias-usuario.md) y las
[decisiones oficiales](decisiones-autenticacion.md).

Alcance vigente desde el 2026-11-23: correo y Google; Apple retirado por decisión
del usuario y pendiente de una decisión futura. Se integró ingreso
automático real tras OTP con US-001.02 y se añadieron sesiones, vinculación segura
y usuarios sembrados. [Guía vigente de proveedores y pruebas](configuracion-acceso-y-pruebas.md).
Los apartados de validación inicial conservan su fecha/evidencia histórica; los
estados y contratos siguientes incorporan la sesión común.

## Organización

- `apps/api/src/registration/`: controlador y DTO para HTTP, servicio de negocio,
  store de persistencia, límites, criptografía, configuración, adaptador Resend y
  filtro de errores. No hay sesiones provisionales ni membresías públicas.
  Este registro crea solo la cuenta CUSTOMER; el propietario de una lavandería
  se establece después, en US-002.01, con rol de membresía OWNER. Las cuentas
  invitadas como STAFF siguen el flujo individual definido en US-003.01.
- `DatabaseService.transaction`: conexión dedicada, rollback y liberación en
  `finally`. Una transacción consume la prueba, crea `accounts` como `CUSTOMER`,
  guarda la credencial y elimina todos los procesos pendientes del contacto.
- `002_customer_registration.sql`: tablas nuevas `account_credentials`,
  `registration_challenges` y `registration_events`. No cambia `001_initial.sql`
  ni modifica cuentas o membresías existentes. UUID para procesos y cuentas.
- `apps/mobile/src/features/registration/`: cliente HTTP, hook del flujo y pantalla;
  `src/app/index.tsx` expone la ruta. El layout usa Stack de Expo Router.

El bloqueo transaccional compartido `74102519` serializa las reservas y consumos
de registro, incluidas las cuotas globales entre instancias API. El hash Argon2id
y el envío remoto ocurren fuera del bloqueo. Es una decisión sencilla para el
MVP; antes de un crecimiento relevante medir contención y sustituir la reserva
global por un mecanismo equivalente, conservando atomicidad y límites.

## Contrato HTTP

Los cuerpos son JSON; no se aceptan propiedades adicionales. Respuestas de este
controlador usan `Cache-Control: no-store`. No registrar cuerpos de estas rutas en
proxies, herramientas de observabilidad ni clientes. Los ejemplos usan fixtures.

| Método y ruta | Cuerpo | Éxito |
| --- | --- | --- |
| `POST /auth/registrations` | `email`, `password` | 201: `registrationId`, `expiresAt`, `resendAvailableAt` |
| `POST /auth/registrations/resend` | `registrationId` UUID v4 | 200: mismo contrato temporal |
| `POST /auth/registrations/verify` | `registrationId`, `code` de seis dígitos | 200: `status: CREATED`, `message`, `sessionToken`, `expiresAt` |

Fechas en ISO 8601 UTC. El correo se recorta y convierte a minúsculas antes de
validar y persistir, sin eliminar puntos ni sufijos `+`. No se solicita teléfono.
Un nuevo registro genera su propio UUID, hash y prueba; no actualiza la contraseña
de otro proceso. Una verificación repetida o perdedora recibe código inválido;
nunca duplica la cuenta ni reemplaza credenciales. Si se pierde la respuesta tras
crear cuenta, reiniciar informa correo registrado y permite ingresar con contraseña.
Desde la integración US-001.02, verificar OTP emite la sesión opaca común de siete días.

| HTTP | `code` | Interpretación |
| --- | --- | --- |
| 400 | `PASSWORD_LENGTH`, `PASSWORD_BLOCKED` | Corregir contraseña |
| 400 | `INVALID_CODE` | Código incorrecto, proceso consumido/inexistente o cinco fallos agotados |
| 400 | `CODE_EXPIRED` | Reenviar código; no reinicia los fallos |
| 400 | validación DTO | `message` puede ser una lista; no incluye valores ni objetos recibidos |
| 409 | `EMAIL_REGISTERED` | Duplicado explícito aprobado; permite enumeración de correos |
| 429 | `RATE_LIMITED` | `retryAfterSeconds` informa espera conservadora; manda el servidor |
| 503 | `EMAIL_UNAVAILABLE`, `REGISTRATION_UNAVAILABLE` | Fallo saneado de transporte, configuración o persistencia |

El contador de fallos se confirma incluso al responder 400. A partir del quinto
fallo se rechaza también el código correcto y el reenvío de ese proceso. Reiniciar
genera otro proceso y conserva las cuotas de envío del contacto/IP. Un reenvío
aceptado invalida inmediatamente el anterior. No afecta un futuro ingreso de una
cuenta existente.

## Protección y retención

Argon2id usa 19.456 KiB, dos iteraciones y paralelismo uno. La contraseña admite
15–128 puntos de código Unicode; no se recorta ni normaliza para hashearla. Solo
se normaliza para comparación local contra `passwords-common` de
`@zxcvbn-ts/language-common` (49.233 entradas en la versión instalada) y una lista
adicional corta de contraseñas evidentes. Es una lista local inicial, no una
comprobación exhaustiva de todas las filtraciones. Mantenerla actualizada al
revisar dependencias. No se envían contraseñas a servicios externos.

OTP aleatorio criptográfico de seis dígitos; HMAC-SHA256 con propósito, UUID,
correo y código. Solo el adaptador de correo recibe el código en memoria;
persistencia y respuestas nunca lo reciben en claro. Cambiar la clave HMAC
invalida procesos pendientes y cambia las claves de las cuotas: no rotarla para
reiniciar límites; coordinar rotación y ventana de cuotas en operación.

Las cuotas son ventanas móviles en PostgreSQL, incluidas reservas fallidas o con
resultado de entrega incierto. El transporte tiene timeout de diez segundos y
clave de idempotencia por envío. No se reintenta silenciosamente. Un fallo inicial
no entrega el UUID al cliente: esperar el enfriamiento e iniciar otro proceso.
El proveedor no confirma por sí solo recepción en la bandeja del destinatario.

Los registros temporales se eliminan al crear cuenta; abandonados y eventos con
más de 24 horas se purgan al atender actividad de registro bajo el mismo bloqueo.
**No hay limpieza en segundo plano ni plazo físico estricto durante inactividad.**
Un proceso de más de 24 horas deja de ser utilizable al reanudarse la actividad.
Antes de producción acordar una política operativa de retención si requiere
eliminación puntual durante inactividad.

## Configuración y ejecución

Completar en el entorno privado, a partir de `.env.example`:

| Variable | Valor inicial / propósito |
| --- | --- |
| `REGISTRATION_HMAC_KEY` | Secreto aleatorio de al menos 32 bytes, estable y compartido entre instancias |
| `RESEND_API_KEY` | Credencial privada del servidor |
| `REGISTRATION_FROM_EMAIL` | Remitente del marketplace en dominio propio verificado |
| `REGISTRATION_EMAIL_HOURLY_LIMIT` | 5, incluye envío inicial |
| `REGISTRATION_IP_HOURLY_LIMIT` | 30 |
| `REGISTRATION_GLOBAL_HOURLY_LIMIT` | 100 |
| `REGISTRATION_GLOBAL_DAILY_LIMIT` | 100 por ventana móvil de 24 horas |
| `REGISTRATION_REQUEST_IP_HOURLY_LIMIT` | 120 solicitudes válidas estructuralmente; limita trabajo de hash/verificación |
| `CORS_ALLOWED_ORIGINS` | Lista explícita separada por comas para clientes web; vacío deniega CORS |
| `EXPO_PUBLIC_API_URL` | URL pública de API del móvil; HTTPS obligatorio en builds de producción |

Las cuotas globales cubren hoy estos envíos. Cuando se implemente recuperación u
otro correo del marketplace, compartir su presupuesto: no crear cuotas paralelas
que permitan exceder el plan del proveedor. Ajustar configuración según consumo.

Express conserva `trust proxy` desactivado: no se acepta `X-Forwarded-For` como
prueba de IP. Si se despliega detrás de un proxy, configurar exclusivamente los
saltos confiables y probar su topología antes de cambiarlo. Terminar TLS en la
infraestructura de despliegue y usar orígenes HTTPS explícitos.

Las dependencias nuevas requieren reconstruir API y móvil y reiniciar Watch:

```powershell
docker compose config --quiet
docker compose up -d --build api mobile
# Detener una sesión Watch anterior antes de iniciar la siguiente.
docker compose watch
```

El arranque `dev:api` ejecuta las migraciones. Revisar historial y conservar
respaldo antes de aplicarlas a datos importantes. Una reversión de código debe
conservar tablas y cuentas; no hay migración destructiva de reversión. En esta
primera validación aislada no se aplicó `002` al volumen persistente; la
comprobación posterior con Docker descrita abajo sí la aplicó y verificó su historial.

## Validación del 2026-11-22

- API: ESLint completo sin `--fix`, build NestJS, 6 pruebas unitarias y 12 e2e
  aprobadas. E2e monta NestJS con Supertest y SQL PGlite en memoria, ejecuta
  `001` y `002` originales y sustituye únicamente pool/transporte. El saludo e2e
  usa un doble de `DatabaseService` y no depende de una base local.
- Reglas cubiertas: normalización, rol forzado, ausencia de cuenta previa al OTP,
  credencial protegida, Unicode/espacios, longitud/lista local, campos extra,
  caducidad, cinco fallos persistidos, reenvío, cuotas por contacto/IP/globales,
  cabeceras de IP falsificadas, fallos de transporte, limpieza, rollback,
  reutilización, concurrencia y vinculación de credenciales entre procesos.
- El adaptador Resend se prueba con fetch simulado; **no acredita entrega real**.
  El motor embebido serializa conexiones: no acredita contención entre conexiones
  independientes del servidor PostgreSQL 17. Repetir carreras en Docker.
- Móvil: lint y TypeScript aprobados. Configuración ESLint añadida con dependencias
  instaladas por `expo install`. Se corrigieron el tipo de ref de la pestaña web
  de plantilla y la detección de hidratación del tema para pasar estos controles.
- Exportación web de Expo aprobada; verifica bundling y renderizado de servidor,
  sin acreditar inspección visual ni comportamiento en dispositivos.
- Argon2id en Windows/Node 24.14.0, 12 muestras secuenciales: mediana 20 ms,
  máximo 23 ms. No es benchmark Docker ni prueba de carga; parámetros mínimos
  iniciales pendientes de medición en el contenedor.
- Compose valida. Docker Desktop estaba detenido; no se reconstruyeron servicios,
  no se verificó la migración en PostgreSQL 17 y no se tocaron volúmenes.

### Comprobación posterior con Docker activo — 2026-11-22

- API y móvil reconstruidos con `pnpm install --frozen-lockfile`; PostgreSQL 17
  saludable. El arranque aplicó `002_customer_registration.sql` al volumen local.
  Historial comprobado: 001 y 002. `/health/database` responde `ok`.
- API: lint completo, build y 6 unitarias aprobadas. E2e ampliado: 13 pruebas
  aprobadas (12 de registro y saludo) con PGlite dentro de Docker.
- La misma batería de 12 pruebas de registro pasó con conexiones independientes
  `pg` contra PostgreSQL 17. El helper `test/registration-database.ts` crea una
  base `registration_test_<UUID>` y elimina exclusivamente esa base al cerrar.
  No trunca tablas de la aplicación. Se verificaron cero bases temporales
  restantes. El modo se activa solo con `REGISTRATION_TEST_POSTGRES=1`.
- La prueba adicional lanza ocho registros concurrentes con un solo envío
  disponible por IP: exactamente uno obtiene 201 y siete reciben 429. La carrera
  de confirmación verifica la credencial del flujo ganador, sin presuponer orden
  entre conexiones.
- Argon2id Linux/Node 24.14.0 en Docker: 12 muestras secuenciales, mediana 20 ms,
  máximo 39 ms, con los parámetros iniciales. Valida costo básico en este equipo;
  no es prueba de carga ni garantía de rendimiento en producción.
- Móvil: lint y tipos aprobados dentro del contenedor. Pantalla inicial inspeccionada
  en navegador: formulario, botón condicionado a datos, mostrar/ocultar,
  envío y mensaje de error del servidor. Captura local en
  `artifacts/us-001.01-front.jpg`.
- Se corrigió `DEV_HOST_IP` local de una dirección anterior a la interfaz Ethernet
  activa, `192.168.1.7`. Se preparó una clave HMAC aleatoria privada y CORS para
  localhost/loopback/LAN; no se muestran ni versionan secretos. API y móvil se
  recrearon para cargar el entorno. El envío visual llegó a la API y recibió
  `EMAIL_UNAVAILABLE`, esperado mientras Resend no está configurado; no creó cuenta.

Pendientes de aceptación: credenciales/remitente/dominio real de Resend, entrega y
carpeta de spam, Android/iOS (teclado, gestores, lectores de pantalla, rotación,
segundo plano, caducidad y reenvío). La confirmación visual en dispositivos no se
sustituye por tipos o inspección web.

## Cómo probar la HU

### App nativa Android/iOS con Expo Go

1. Conectar teléfono y computador a la misma red; el computador puede usar Ethernet.
2. Abrir Expo Go e ingresar con la misma cuenta Expo que reconoce la CLI dentro
   del servicio `mobile`. El login de Expo es independiente de las cuentas del marketplace.
3. Consultar el QR con `docker compose logs --tail 80 mobile` y escanearlo desde
   Expo Go en Android o la cámara en iPhone. Metro publica `exp://192.168.1.7:8081`.
4. La aplicación nativa se ejecuta en el teléfono. Verificar allí teclado, gestores,
   accesibilidad y comportamiento de la HU; abrir la versión web no acredita esto.

Incidencia confirmada el 2026-11-22: el ingreso por navegador/Google se había
completado en Windows, pero la CLI del contenedor seguía sin sesión. Con autorización
explícita del usuario se reutilizó únicamente la sesión Expo en el contenedor móvil
local, con archivo privado modo `600`, sin guardar secretos en repositorio, imagen,
logs ni documentación. Tras reiniciar Metro, `expo whoami` reconoció la cuenta y
la petición del manifiesto iOS respondió HTTP 200 con recurso de lanzamiento.
Sigue pendiente observar la apertura y el formulario en el teléfono del usuario.

Tras repetirse la incidencia, `compose.yaml` monta el volumen exclusivo
`expo_cli_state` en `/root/.expo`: conserva la sesión al reconstruir o recrear
`mobile`, sin montar el perfil de Windows. Directorio `700` y archivo de sesión
`600`; no copiar su contenido al repositorio. Recreación forzada comprobada el
2026-11-22: `expo whoami` siguió reconociendo la cuenta.
Si se necesita renovar
el acceso con Google, el flujo es por navegador; `login --no-browser` pide credenciales
de Expo y no permite elegir Google. No copiar sesiones entre entornos sin autorización.

### Vista web complementaria

Los tres servicios quedan levantados. Abrir [frontend web local](http://localhost:8081)
o, desde un navegador de la misma red, [frontend LAN](http://192.168.1.7:8081).
Si DHCP cambia la IP de Ethernet, actualizar `DEV_HOST_IP`, el origen LAN de
`CORS_ALLOWED_ORIGINS` y recrear API/móvil. No usar `localhost` en el teléfono para
referirse al computador. La interfaz web no sustituye la prueba nativa Android/iOS.

Para completar el registro real:

1. Configurar en `.env` privado `RESEND_API_KEY` y `REGISTRATION_FROM_EMAIL`, con
   dominio/remitente propio verificado en Resend. La clave HMAC local ya quedó
   preparada. No enviar credenciales por chat ni guardarlas en notas.
2. Aplicar solo el cambio de entorno:

   ```powershell
   docker compose up -d --no-deps --force-recreate api
   ```

3. Introducir un correo propio y una contraseña nueva de 15–128 caracteres. Pulsar
   **Enviar código**, revisar bandeja/spam y copiar los seis dígitos.
4. Introducir un código incorrecto para comprobar error y luego el correcto para
   ver **Tu cuenta está lista**. La creación no inicia sesión: corresponde a US-001.02.
5. Con otro registro, probar reenvío tras 60 segundos: código anterior inválido;
   nuevo válido. Cinco errores agotan el proceso; vencimiento a diez minutos
   permite solicitar otro código sin reiniciar los fallos. Los límites pueden
   responder 429; no borrar cuotas para repetir la prueba.
6. Repetir con el correo ya creado: aparece el duplicado explícito.

Sin Resend configurado se puede inspeccionar el formulario y comprobar el error
de envío; no es posible completar manualmente el OTP. No hay código fijo ni
endpoint de desarrollo que exponga OTP. La lógica completa puede comprobarse ahora
con el transporte aislado de la batería automatizada:

```powershell
docker compose exec -T api pnpm --dir apps/api test --runInBand
docker compose exec -T api pnpm --dir apps/api test:e2e --runInBand
docker compose exec -T -e REGISTRATION_TEST_POSTGRES=1 api pnpm --dir apps/api test:e2e --runInBand registration.e2e-spec.ts
```
